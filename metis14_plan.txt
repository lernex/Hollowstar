Metis-1.4 Plan

Status:
- Living draft.
- Seeded from Metis-1.3 lessons, but this file is mainly for early Metis-1.4 infra and workflow decisions.
- Update this file incrementally as Metis-1.3 finishes and Metis-1.4 scope becomes clearer.

Current baseline assumption:
- Metis-1.4 should inherit the strongest Metis-1.3 data-quality and post-training lessons unless a later eval shows we should change direction.
- The biggest already-decided Metis-1.4 change is infrastructure: larger CPU prep should move off Runpod and onto AWS local NVMe.

Name

- Metis-1.4

Current planning goals

- scale beyond the more cramped Runpod CPU-prep setup used for Metis-1.3
- keep GPU time focused on actual training
- make preprocessing faster by using stronger CPU boxes and fast local NVMe scratch
- preserve a clean handoff into Runpod GPU training

Current fixed infrastructure decision

CPU prep provider:
- AWS

Chosen current CPU prep instance:
- i7i.4xlarge

Current AWS spec for the chosen prep box:
- 16 vCPU
- 128 GiB RAM
- 1 x 3750 GB NVMe SSD
- up to 25 Gigabit network bandwidth
- official us-east-1 Linux on-demand price: $1.5101/hour

Why this is the current pick:
- much stronger CPU headroom than the small Runpod CPU pods used for Metis-1.3 prep
- enough RAM that preprocessing should stay comfortable without over-optimizing around tiny memory ceilings
- large local NVMe scratch so tokenizer sampling, tokenization, shard writing, and temporary data prep can stay on fast local storage
- still cheaper than moving all the way up to a larger 32-vCPU NVMe box before Metis-1.4 proves it needs that scale

Current infrastructure philosophy

Hot path:
- do CPU-heavy preprocessing on AWS local NVMe, not on shared network storage

Durability:
- do not treat AWS local NVMe as the only copy of finished work
- copy finished artifacts off the instance after each completed stage

GPU training:
- keep GPU training on Runpod unless a later scaling step makes same-cloud training more attractive

Recommended AWS -> Runpod handoff shape

Stage 1: AWS CPU prep
- clone repo
- install CPU-prep-only dependencies
- use local NVMe as the active scratch workspace
- train tokenizer
- build final pretraining binaries or shards
- build final chat SFT data
- build final reasoning SFT data
- render final Hugging Face assets and plan metadata

Stage 2: Durable staging
- copy finished artifacts off the AWS NVMe before terminating the instance
- preferred durable staging target: S3
- acceptable direct handoff for smaller runs: copy finalized artifacts straight to the Runpod network volume

Stage 3: Runpod GPU training
- attach the Runpod network volume
- read finalized tokenizer and training artifacts from that volume
- run base training, chat SFT, reasoning SFT, eval, and release export there

Why AWS local NVMe is the key speed lever

- preprocessing hot spots are tokenization, shard writing, temporary files, and repeated local read/write churn
- local NVMe should be materially faster for this workload than treating shared network storage as the main scratch disk
- this keeps the expensive GPU box from wasting time on downloads, tokenization, and preprocessing

Current expected speedup versus the small Metis-1.3 Runpod CPU pods

- conservative expectation: about 1.5x faster
- likely expectation: about 2x-3x faster
- best-case on the heavier data-build stages: about 3x-4x faster

Important caveat:
- do not assume linear speedup from vCPU count alone
- real gains depend on tokenizer behavior, dataset streaming overhead, shard layout, and how parallel the prep pipeline actually becomes

Storage rules

Use AWS local NVMe for:
- tokenizer sample files
- temporary text shards
- temporary token shards
- pretraining build scratch
- temporary chat/reasoning prep outputs

Do not leave as the only copy on AWS local NVMe:
- final tokenizer assets
- final pretraining artifacts
- final chat/reasoning datasets
- plan metadata

Copy these off before instance shutdown:
- tokenizer files
- final pretraining binaries or shards
- final chat SFT outputs
- final reasoning SFT outputs
- plan and config metadata

Open model decisions still intentionally left undecided

- final parameter count
- final token budget
- final context length
- whether Metis-1.4 keeps the exact Metis-1.3 backbone family or changes it again
- exact pretraining and post-training mixes

Rule for now:
- keep Metis-1.4 architecture/data decisions open until Metis-1.3 finishes and gives us real evidence
- keep the AWS CPU-prep decision as the current infra default unless later profiling shows we should jump to a larger 32-vCPU NVMe instance
